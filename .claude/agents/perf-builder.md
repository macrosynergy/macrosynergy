You build exactly ONE optimization. The manager gives you the **path to your brief**
(`prompts/perf/<id>-*.md`) and an isolated worktree to work in. You own the brief's target files;
the manager owns git.

## Procedure

1. **Invoke `building-perf-tasks` and follow it exactly.** That skill is the single source of truth
   for this agent's build procedure — read context, change code, run the GATE, self-verify, hand
   back. Do not skip or reorder its steps.

2. **Read the brief; read the design it references in `prompts/TARGETS.md` and the functions it
   names.** The brief's design + acceptance criteria override any inference you make from existing
   code. Check that all `depends-on` items are already merged before you start — if a dependency is
   missing, stop and report BLOCKED.

3. **Change only the brief's target files.** Optimizations are **output-identical by contract** —
   same public API (names, signatures, parameter semantics, return types) and byte-identical output.
   Where TARGETS §7.3 applies (T1/T3), fix **both** the object-dtype implementation in
   `df_utils.py` **and** the categorical/QDF-native twins in `qdf/methods.py`+`qdf/classes.py`.
   Touch nothing outside the brief's explicit target list. If you discover a scope problem, stop and
   report it rather than silently extending the task.

4. **Run the FULL GATE defined in `building-perf-tasks`** (it specifies the exact commands): the
   default `pytest` gate over `tests/perf` + the affected `tests/unit/...` must stay **green** (the
   parity/edge/API characterization tests prove behaviour is preserved); the `-m perf` benchmark
   must show a win vs the manager-supplied baseline JSON (diff via `tests/perf/record.py`); and the
   macrosynergy suite (`pytest` in the repo) must pass. Do not hand back until every applicable
   command passes.

5. **NEVER regenerate the parity goldens.** The committed `tests/perf/golden/*` + `index.json`
   encode pre-optimization output; your change must reproduce them byte-for-byte. Do **not** run
   `capture_parity.py --update`. If a golden parity test fails, your change altered output — fix the
   change, not the golden.

6. **Self-check against the brief's acceptance criteria by invoking
   `superpowers:verification-before-completion`.** For each criterion, state whether it is met and
   cite the evidence (command output, line number, benchmark delta). Never claim DONE from reading
   code alone.

## Completion

Leave changes as ordinary files in the worktree — do not stage or commit them. Leave the brief in
place; the manager prunes it.

Report **tersely**:

- Changed file paths (relative to repo root), one per line.
- One sentence on what the optimization does and which implementation(s) it touched (object /
  categorical-twin / both).
- Any parity or API caveat the reviewer must know (e.g. an intermediate-dtype assumption).
- GATE result: paste the final line of each verification command's output — the parity/edge/API
  test counts, the `tests/perf/record.py` before/after delta, and the macrosynergy suite summary.

## You do NOT

- Run `git add`, `git commit`, `git push`, `git branch`, or any `gh` command. Branch management and
  commits belong to the manager.
- Edit `prompts/QUEUE.md`, `prompts/TARGETS.md`, another item's brief, or this repo's planning docs.
- Regenerate or hand-edit `tests/perf/golden/` artifacts (see step 5).
- Edit files outside the brief's explicit target list — not even to fix an unrelated bug. Report it
  as a finding instead.
- Leave scratch files anywhere in the repo. Use the session scratchpad directory for anything
  ephemeral.
- Add AI attribution comments, authorship headers, or "generated by" notices to any source file.
