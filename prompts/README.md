# macrosynergy performance — work queue & how to drive it

This directory holds the performance optimization **book of work** for `feature/performance` and the
**queue** that a manager/creator/reviewer agent team drains one item at a time. Nothing here merges
to `develop`/`main` — all work stays on `feature/performance` until a human promotes it.

## Documents

| File | What it is |
|---|---|
| [`TARGETS.md`](TARGETS.md) | The diagnosis: per-cell baseline, ranked targets (T1–T7), each target's design, the **GATE** (§5) and how the in-repo `tests/perf` framework backs it (**§5.1**), and the QDF-native analysis (§7). |
| [`QUEUE.md`](QUEUE.md) | The work queue. One row per `perf/<slug>` item (Q1–Q8), with status, baseline, and the before/after table to fill on completion. |
| [`perf/`](perf/) | Per-item **builder briefs** (`Q<k>-*.md`) — the detailed contract a builder implements: goal, target files, the exact GATE commands, and acceptance criteria. |

## The team (in `.claude/`)

Mirrors the academy `run-research-pipeline` and knowledge `run-parse-pipeline` pattern, adapted to
package optimization:

| Component | Where | Role |
|---|---|---|
| **`run-perf-queue`** | `.claude/skills/run-perf-queue/` | **Manager** — owns git/gh, worktrees, the QUEUE, and the benchmark baselines. Drains the queue in dependency order, **serially (N=1) by default**, integrating via per-item PRs into `feature/performance`. |
| **`perf-builder`** | `.claude/agents/perf-builder.md` | **Creator** — implements ONE item in an isolated worktree against its brief + the GATE. Writes package code; never touches git/queue; never regenerates parity goldens. |
| **`perf-reviewer`** | `.claude/agents/perf-reviewer.md` | **Reviewer** — read-only, adversarial. Re-runs the GATE itself and returns `APPROVE`/`CHANGES`. |
| `building-perf-tasks` | `.claude/skills/building-perf-tasks/` | The build procedure + the GATE commands the builder follows. |
| `reviewing-perf-tasks` | `.claude/skills/reviewing-perf-tasks/` | The review rubric, severity rules, and verdict format. |

## How to run it

Invoke the manager skill from a Claude Code session at the repo root:

```
run-perf-queue            # drive the next claimable item (lowest Q-number whose deps are DONE)
run-perf-queue Q1         # drive a specific item
run-perf-queue Q1 N=2     # raise parallelism — ONLY if the selected items touch disjoint files
```

Default is **N=1 (strictly sequential)** — most items optimize shared, broad-blast-radius files
(`df_utils.py`, the `qdf/` twins, `signal_return_relations.py`), so serial is the safe default.

The manager then, per item: sets the QUEUE row `IN PROGRESS` → captures the pre-change benchmark
baseline on `feature/performance` → provisions a worktree `perf/<slug>` → dispatches `perf-builder`
→ dispatches `perf-reviewer` → revises up to 3 rounds → on `APPROVE`, commits the target files, opens
a PR into `feature/performance`, merges, re-runs the GATE on the merged tree, fills the QUEUE
before/after row, marks the item `DONE`, and removes the worktree.

### Recommended order

`Q1 (T2c)` → `Q2 (T1)` → `Q3 (T2)` → `Q4 (T3)` → `Q5 (T4)`, then `Q6 (T5, needs Q4)`, `Q7 (T6)`,
`Q8 (T7, optional, needs Q4)`. See the ranking rationale in `TARGETS.md` §3.

## The GATE (what every item must pass — `TARGETS.md` §5 / §5.1)

The in-repo `tests/perf/` framework is the per-item gate (see [`../tests/perf/README.md`](../tests/perf/README.md)):

1. **API unchanged** — `inspect.signature` tripwires in the appended `tests/unit/...` classes.
2. **Output parity** — `tests/perf/test_parity_*.py` golden snapshots + edge/dtype tests stay green
   (byte-identical output). **Goldens are never regenerated by an item** — the optimization must
   reproduce them.
3. **Measurable win** — `pytest tests/perf -m perf --benchmark-only -n0 --no-cov --benchmark-json=…`
   before/after, diffed by `python tests/perf/record.py <baseline> <after>` (cross-machine guard).
4. **Suite passes** — `pytest` in `~/repos/macrosynergy` (benchmarks deselected by `-m 'not perf'`).

Run the default gate (parity/edge/API, benchmarks excluded) any time with plain `pytest`; run a
benchmark sweep with `pytest tests/perf -m perf --benchmark-only -n0 --no-cov`.

## Adding a new item

1. Add a row to `QUEUE.md` (status `TODO`, slug, cells, baseline, depends-on).
2. Write a builder brief `perf/Q<k>-<slug>.md` — copy `perf/Q1-t2c-qdf-ticker-series.md` as the
   template: Goal, the `TARGETS.md` design reference, **Files** (exact targets; note §7.3 if the
   target has object + categorical twins), the **GATE** commands, and **acceptance criteria**.
3. Ensure the item's `tests/perf` benchmark + parity + edge/API coverage exists (TARGETS §5.1 lists
   the current coverage and the gaps — e.g. Q7/T6 needs a new categorical-`Basket` test).
